## 3. Important concepts explained

### 3.1 Explicit feedback

Explicit feedback is information a user deliberately provides to communicate an opinion.

Examples:
- Giving a film 4 out of 5 stars.
- Selecting a thumbs-up or thumbs-down.
- Submitting a review score.

The user directly tells the system what they think.

### 3.2 Implicit feedback

Implicit feedback is collected from behaviour rather than a direct rating.

Examples:
- Playing a song.
- Replaying a song.
- Saving a song.
- Clicking a product.
- Watching a video.
- Purchasing an item.

These actions can suggest interest, but they are ambiguous. For example, a video may play automatically even when the user is not interested. A missing interaction also does not necessarily mean dislike: the user may not have seen the item.

### 3.3 Event log

An event log is a table of recorded actions. In this lab, each row contains:

- `user_id`: the person who performed the action.
- `item_id`: the track involved.
- `event_type`: the action that occurred.

The notebook generates 12 users (`U01` to `U12`) and 18 tracks (`Track_01` to `Track_18`). It generates multiple events for some user–track pairs.

### 3.4 Interaction weight and strength

The notebook assigns a numerical weight to each action:

| Event | Weight |
|---|---:|
| `play` | 1.0 |
| `repeat_play` | 3.0 |
| `save` | 5.0 |

The weights represent an assumption: a save is treated as a stronger signal than a normal play, and a repeat play is treated as stronger than one play.

The notebook then adds the weights for each user–track pair. This total is called `strength`.

**Example:** If a user plays a track once and saves it once, the strength is:

`1.0 + 5.0 = 6.0`

These values are only demonstration choices. A real recommender team should test whether the weights make sense for its application.

### 3.5 Preference

Preference answers:

**Was positive behaviour observed for this user–item pair?**

In this lab:
- `1` means an interaction was observed.
- `0` means no positive interaction was observed.

Preference is binary. It does not tell us how many times an item was used.

### 3.6 Confidence

Confidence answers:

**How strongly should the model trust the observed interaction?**

The lab calculates confidence using:

\[
c_{ui} = 1 + \alpha r_{ui}
\]

Where:
- \(c_{ui}\) = confidence for user \(u\) and item \(i\).
- \(\alpha\) = confidence scaling value.
- \(r_{ui}\) = interaction strength.

The notebook uses `alpha = 20`.

For example:
- Strength 1 gives confidence `1 + (20 × 1) = 21`.
- Strength 6 gives confidence `1 + (20 × 6) = 121`.

Both examples have preference 1, but the second has higher confidence.

**A note about the implementation:** The notebook displays the confidence calculation as a separate column to explain the concept. It passes the raw interaction-strength matrix to the `implicit` library; the model uses its `alpha` setting during training.

### 3.7 Sparse user–item matrix

A user–item matrix organises interaction data:

- Rows represent users.
- Columns represent items.
- Cell values represent interaction strengths.

Most users interact with only a small proportion of all available items. Therefore, most matrix cells are zero or unobserved.

A **sparse matrix** stores the non-zero values efficiently rather than storing every empty cell. The notebook uses SciPy's CSR (Compressed Sparse Row) format.

### 3.8 ALS – Alternating Least Squares

ALS is a collaborative-filtering method. It learns numerical representations called **latent factors** for users and items.

The model alternates between updating user factors and item factors. These factors help it estimate which items may be relevant to a user based on patterns across the interaction matrix.

The lab uses:
- `factors=16`
- `regularization=0.10`
- `alpha=20`
- `iterations=25`
- `random_state=4060`

`factors` controls the number of learned dimensions. `regularization` helps control overfitting. `iterations` controls how many training rounds are performed. `random_state` helps make the demonstration repeatable.

### 3.9 Top-N recommendation

A recommender should produce a ranked list of items, not merely learn a model.

The notebook requests the Top 5 tracks for user `U01`. It filters out items already present in the user's observed history.

The scores are **ranking scores, not probabilities**. A score of 0.8 should not be interpreted as an 80% probability of liking a track.

### 3.10 Evaluation

A recommender should be tested on interactions that were not used to train it.

A time-aware evaluation can:
1. Sort a user's interactions by time.
2. Train on earlier interactions.
3. Hold out later interactions.
4. Recommend items not already seen.
5. Measure whether the held-out items appear near the top.

Common ranking metrics include:
- **Precision@K:** How many of the recommended K items were relevant?
- **Recall@K:** How many of the relevant held-out items were found in the Top K?
- **NDCG@K:** How well were relevant items placed near the top of the ranking?

The synthetic data in this lab has no timestamps. Therefore, the notebook explains the evaluation design but does not claim to produce a valid time-based evaluation score.

- **Markdown cell:** Contains headings, explanations, lists, links, equations, and tables.

## 8. Common problems and solutions

### `ModuleNotFoundError`

The package may not be installed in the Python environment selected by the notebook.

- Check **Select Kernel**.
- Install using the terminal for that environment or run `%pip install ...` in the notebook.
- Restart the kernel and rerun the cells.

### The notebook uses the wrong Python interpreter

Select the `.venv` environment from **Select Kernel**. The VS Code terminal interpreter and notebook kernel should point to the same environment.

### PowerShell refuses to activate `.venv`

Use the environment's Python executable directly:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip install ipykernel
```

You can still select `.venv` as the notebook kernel without activating it in the terminal.

### Package installation fails

Check your Python version and internet connection. If a package does not provide a compatible build for your Python version, use a fresh Python 3.11 or 3.12 environment. Do not install packages into a different interpreter and assume the notebook will see them.

### Recommendation indices or mapping errors

Run the notebook from the beginning. The user and item mappings, matrix, and model must all be built from the same version of the `interactions` table.

### Recommendations are empty

Check that the requested number of recommendations is smaller than the number of available items and that the user has not interacted with every item.

## 9. Academic discussion and limitations

This is a small teaching demonstration, not a production recommender system.

Its limitations include:

- The event data is synthetic.
- It has only 12 users and 18 tracks.
- The data has no timestamps.
- The event weights are assumptions.
- It uses interaction behaviour only and does not include track descriptions, genres, artists, or other metadata.
- It demonstrates one user’s Top-5 list rather than a full user study.
- It does not establish that the recommendations improve user satisfaction.

Possible next improvements include adding timestamped real data, comparing alternative event weights, adding a popularity baseline, calculating ranking metrics with a suitable train/test split, and testing recommendation coverage and popularity bias.
